# Release engineering and disaster recovery

This runbook covers reproducible installs, probes, metrics, backups, recovery and the signed image release path introduced in upgrade Node 11.

## Reproducible installation

`pyproject.toml` keeps publishable compatibility ranges. `uv.lock` is the deployment source of truth for Python 3.11 and 3.12. CI and both Docker images reject lock drift.

```bash
uv lock --check
uv sync --locked --extra dev   # development and CI
uv sync --locked --no-dev      # production dependencies
```

`requirements.lock` is an autogenerated, hash-checked compatibility export. Regenerate both files intentionally after dependency changes:

```bash
uv lock
uv export --locked --no-dev --format requirements.txt \
  --no-emit-project --output-file requirements.lock
```

## Probes and metrics

- `GET /healthz` is process liveness only. It never checks keys, storage, providers or workers.
- `GET /readyz` verifies API key material, SQLite integrity, the current migration version and the on-demand session worker configuration. It returns HTTP 503 when a required check fails.
- `GET /metrics` uses the normal Bearer token and exports Prometheus metrics for HTTP latency/status, durable queue depth, workers, provider latency/failure, cache events, LLM tokens and backtest duration.

Application logs default to one JSON object per line in server mode. Correlation fields include `request_id`, and job execution adds `session_id` and `job_id`. Set `VIBE_TRADING_LOG_FORMAT=text` only for an interactive local session. Existing secret-redaction filters are applied to the JSON handler.

Suggested alerts:

- readiness is non-200 for 2 consecutive minutes;
- non-LLM HTTP P95 exceeds 300 ms for 5 minutes;
- `pending + retry_wait` queue depth grows for 10 minutes;
- provider failure ratio exceeds 20% over 15 minutes;
- any terminal failed job appears without a corresponding user-visible attempt failure.

## State backup and restore

Backups use SQLite's online backup API and produce a SHA-256 manifest. Keep backups outside the active state volume.

```bash
scripts/state-admin backup /secure/backups/vibe-$(date +%F).db
scripts/state-admin verify /secure/backups/vibe-2026-07-18.db
```

Restore is deliberately two-step: stop the API first, verify the backup, then pass `--confirm`. The command retains the old database as a timestamped pre-restore backup and atomically replaces the target only after the restored temporary database passes integrity checks.

```bash
docker stop --time 30 vibe-trading
scripts/state-admin verify /secure/backups/vibe-2026-07-18.db
scripts/state-admin restore /secure/backups/vibe-2026-07-18.db --confirm
docker start vibe-trading
curl --fail http://127.0.0.1:8899/readyz
```

Run the backup/restore drill before every release candidate and at least monthly. The deterministic automated drill is `test_state_backup_and_atomic_restore_drill`.

Recommended local-service objectives are RPO ≤24 hours with daily backups and RTO ≤30 minutes. Deployments that need a lower RPO must shorten the backup interval or use replicated storage; the local SQLite mode must not be described as zero-data-loss.

## Cache governance

The cleanup command is dry-run by default and only inspects the explicit loader-cache root. Review its counts before adding `--apply`.

```bash
scripts/state-admin cache-cleanup --older-than-days 30
scripts/state-admin cache-cleanup --older-than-days 30 --apply
```

OAuth token caches and durable state are intentionally outside this command's scope.

## Container and release path

The production image is multi-stage: compilers remain in the builder, the runtime uses a fixed non-root UID, readiness is the health check, and SIGTERM has a 30-second Compose grace period. Validate locally with:

```bash
docker build -t vibe-trading:node11 .
scripts/test-production-container vibe-trading:node11
```

`.github/workflows/release.yml` builds multi-architecture images on `v*` tags, pushes to GHCR, emits SBOM and SLSA provenance attestations, adds a GitHub artifact attestation, performs keyless Cosign signing and blocks every Critical/High vulnerability finding. A tag is not a production approval by itself; the seven-day RC observation record and all CI gates still have to be accepted.

The release job scans the immutable digest before signing, verifies both the keyless signature and GitHub attestation after signing, and uploads `node11-release-evidence.json`. That artifact is the hand-off to RC observation; do not copy a mutable image tag into the RC record.

Both pull-request CI and release CI run Trivy with `ignore-unfixed: false`. The action is pinned to the full SHA of immutable safe release 0.35.0, following the [Trivy ecosystem incident advisory](https://github.com/aquasecurity/trivy/security/advisories/GHSA-69fq-xp46-6x23). Never replace this with a mutable tag or blanket `ignore-unfixed`.

If an upstream-only finding must be risk-accepted, record every CVE explicitly with affected package, image digest, exploitability assessment, compensating controls, owner and an expiry of at most 30 days. The user must explicitly accept that list before an ignore policy is added. A base-image refresh or available vendor fix immediately invalidates the exception and requires a new scan. At the Node 11 validation point, the pinned Ubuntu 24.04 image has zero Critical/High findings in both OS and Python layers, so the strict gate passes without an exception.

Verify a published release with its immutable digest:

```bash
cosign verify \
  --certificate-oidc-issuer=https://token.actions.githubusercontent.com \
  --certificate-identity-regexp='^https://github.com/HKUDS/Vibe-Trading/' \
  ghcr.io/HKUDS/Vibe-Trading@sha256:...
gh attestation verify oci://ghcr.io/HKUDS/Vibe-Trading@sha256:... \
  -R HKUDS/Vibe-Trading
```

## Release-candidate observation

`.github/workflows/node11-rc.yml` is manually dispatched once per day with the same immutable 40-character candidate commit and GHCR `@sha256:` reference. Each run performs the production container smoke test, a five-minute readiness soak sampled every five seconds, deterministic performance/queue checks, the atomic backup/restore drill and a strict Trivy scan. It uploads `node11-rc-day-N.json` even when a gate fails.

For seven consecutive days, retain one accepted JSON record and one row in `node-11-rc-observation.md` with commit/digest, workflow run, readiness uptime, API P95, maximum queue depth, lost-job count, Critical/High findings, backup/restore drill result and blocking incidents. All seven records must use exactly the same commit and digest. A failed run, a blocking incident, or any candidate change resets the window to Day 1. A short local soak is only preflight evidence and cannot be counted as an RC day.

After the candidate release evidence provides the immutable digest, dispatch a day with:

```bash
gh workflow run "Node 11 RC observation" \
  --ref "$candidate_sha" \
  -f candidate_sha="$candidate_sha" \
  -f image_ref="ghcr.io/OWNER/vibe-trading@$digest" \
  -f rc_day=1
```

Node 11 cannot claim this time-based gate before all seven daily artifacts are accepted or the user explicitly accepts a waiver.
